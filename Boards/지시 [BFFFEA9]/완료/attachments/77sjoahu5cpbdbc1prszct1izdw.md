# GitHub 협업 및 브랜치 운영 계획

개발팀장 강주영과 개발팀 멘토 이강민은 작업지시서와 GitHub Issues, 브랜치를 다음과 같이 연결하여 관리한다.

## 1. 작업 관리

- **작업지시서 카드**: 개발 범위, 담당자, 일정 및 완료 기준을 관리한다.
- **GitHub Issues**: 구현 과정에서 발생한 세부 작업, 버그의 재현 절차 및 로그, 코드 수정이 필요한 사항과 관련 논의를 기록한다.
- 작업지시서와 관련된 GitHub Issue가 생성된 경우 카드에 **Issue 링크**를 첨부하여 서로 추적할 수 있도록 한다.
- 일정 및 시연에 영향을 줄 수 있는 문제는 기존 원칙에 따라 **Mattermost 리스크 및 이슈 등록부**에도 별도로 기록한다.

## 2. 브랜치 운영

기본 브랜치는 `main`, 개발 통합 브랜치는 `dev`로 운영한다.

- `main`: QA가 완료된 배포 가능한 코드
- `dev`: 현재 개발 중인 기능들이 통합되는 브랜치
- `feat/*`: 기능 개발 브랜치
- `fix/*`: 일반적인 버그 수정 브랜치
- `hotfix/*`: 운영 중 긴급하게 수정해야 하는 문제를 처리하는 브랜치

일반적인 기능 개발은 `dev`에서 `feat/*` 브랜치를 생성하여 진행하고, 완료 후 Pull Request를 통해 `dev`에 병합한다.

## 3. 개발 및 병합 흐름

일반 개발은 다음 흐름으로 진행한다.

`작업지시서 → GitHub Issue → feat/* 브랜치 → PR → dev → QA → main`

기능 개발이 완료되면 PR을 생성하고 검토 후 `dev`에 병합한다. 스프린트 또는 정해진 개발 범위의 기능들이 `dev`에 모두 반영되면 해당 버전을 기준으로 QA를 진행한다.

QA가 완료되고 배포 가능한 상태임을 확인한 뒤 `dev`를 `main`에 병합한다.

## 4. Hotfix

배포된 `main`에서 긴급한 수정이 필요한 경우에는 `main`에서 `hotfix/*` 브랜치를 직접 생성한다.

수정 후 `main`을 대상으로 PR을 생성하고 검토 후 바로 병합한다. 이후 동일한 수정 사항이 이후 개발 과정에서 누락되지 않도록 `dev`에도 반영한다.

## 5. 검토 및 병합

- `feat/*`, `fix/*` → `dev`: 작업자가 PR을 생성하고 개발팀 내 검토 후 병합한다.
- `dev` → `main`: 해당 개발 범위의 QA 완료 후 병합한다.
- `hotfix/*` → `main`: 긴급 수정 내용을 검토한 뒤 병합하고 `dev`에도 반영한다.
- PR에는 가능한 경우 관련 작업지시서 또는 GitHub Issue를 연결하여 변경 목적을 확인할 수 있도록 한다.

## 결정 필요 사항

PR에 대해서 누가 리뷰를 담당하고 시간을 얼마 정도로 둘지에 대해 결정이 필요.
