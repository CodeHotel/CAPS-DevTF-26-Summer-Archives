# GPU 대여 서비스 교내망 조사 보고서

측정 기간: 2026년 9월 22일 ~ 9월 25일  
측정 대상: 교내 GPU1과 GPU2, 외부 노트북, 테스트용 AWS EC2

## 1. 조사 목적과 범위

외부 사용자의 SSH 접속과 파일 전송에 적합한 방식을 제안하기 위해, 교내 GPU 서버의 연결 조건을 조사하고 상시 중계 방식과 NetBird 오버레이 방식의 성능을 비교했습니다.

담당자 안내에 따르면 교내망은 아웃바운드 연결을 허용하고 외부에서 시작하는 인바운드 연결은 기본적으로 차단합니다. 이 조건에서 접속 가능한 경로를 확인하기 위해 NAT 동작과 UDP 통신 가능 여부를 조사하고, 중계 서버 경유 경로와 P2P 경로의 RTT 및 처리량을 측정했습니다.

조사는 교외에서 GPU 서버에 원격 접속해 수행했습니다. 측정 범위는 두 GPU의 NIC 상태, 서버 간 통신, 외부 접속 성능입니다. NAS는 현재 장비가 없어 향후 교내망에 설치하는 구성을 검토했습니다.

## 2. 교내 네트워크 환경

### 2.1 외부 접속 조건과 경로

담당자 안내에 따르면 GPU1과 GPU2는 신공학관 6층에 있습니다. 두 서버는 같은 내부 주소 대역과 기본 게이트웨이를 사용하며, STUN 검사에서는 같은 공인 IP가 관측됐습니다.

| 항목 | GPU1 | GPU2 |
|---|---|---|
| 내부 IP | `192.168.*.2` | `192.168.*.176` |
| 기본 게이트웨이 | `192.168.*.1` | `192.168.*.1` |
| 외부에서 관측한 공인 IP | `210.94.*.33` | `210.94.*.33` |

![교내 GPU 서버와 외부 테스트 장비의 연결 구조](교내망_연결구조.png)

위 그림은 라우팅 정보와 `traceroute`, 담당자 안내를 바탕으로 추정한 논리 구조입니다.

외부 STUN 서버와의 UDP 통신 및 EC2와의 TCP 통신은 성공했습니다.

### 2.2 NIC 연결 속도

`ethtool`로 지원 속도와 실제 연결 속도를 확인했습니다.

| 장비 | 네트워크 인터페이스 | 지원 최대 속도 | 실제 연결 속도 |
|---|---|---:|---:|
| GPU1 | `enp4s0` | 1Gbps | 100Mbps |
| GPU2 | `enp2s0` | 1Gbps | 1Gbps |

이후 오버레이 테스트은 NIC가 1Gbps로 연결된 GPU2에서 진행했습니다.

### 2.3 GPU1과 GPU2 사이의 통신

상대 서버로 향하는 경로에는 게이트웨이가 없었고, 이웃 테이블의 MAC 주소는 실제 상대 NIC의 MAC 주소와 일치했습니다. 이를 근거로 두 서버가 같은 L2 네트워크에서 직접 통신한다고 판단했습니다.

iperf3로 양방향 TCP 전송을 각각 3회, `ping`으로 방향별 응답 30회를 측정했습니다.

| 데이터 방향 | 평균 수신 처리량 | ping 평균 RTT | ping 응답 손실 |
|---|---:|---:|---:|
| GPU1 → GPU2 | 94.10Mbps | 0.387ms | 0/30 |
| GPU2 → GPU1 | 94.10Mbps | 0.261ms | 0/30 |

처리량은 매회 94.1Mbps로 GPU1의 100Mbps 링크 제한과 부합했습니다.

## 3. 외부 접속 성능의 측정 기준

### 3.1 RTT 측정

두 접속 경로의 RTT는 iperf2의 TCP bounceback으로 측정했습니다. `ssh -L`은 TCP 포트포워딩이므로 ICMP ping을 전달하지 않습니다. 중계 서버를 대상으로 한 ping이나 로컬 TCP 소켓의 RTT로는 GPU까지의 전체 경로를 측정할 수 없어, GPU의 측정 프로그램이 요청을 받고 응답하는 bounceback을 사용했습니다.

| 항목 | 측정 조건 |
|---|---|
| 요청과 응답 크기 | 각각 100바이트 |
| 요청 간격 | 1초 |
| 서버 대기 시간 설정 | 0초 |
| 반복 횟수 | 경로별 약 30초씩 3회, 총 90개 응답 |
| 비교 지표 | 평균 RTT, 최대 RTT, 타임아웃 |

RTT는 연결이 완료된 상태에서 측정했습니다.

### 3.2 TCP 처리량 측정

중계 서버와 NetBird 경로는 iperf2의 TCP 연속 전송으로 비교했습니다. GPU 서버 간 통신과 GPU에서 EC2로 보내는 아웃바운드 테스트은 iperf3 결과를 사용했습니다.

3회 반복한 TCP 테스트은 회당 약 30초 동안 수행했고, 회차별 처리량의 산술평균을 제시했습니다. 수신 측 결과를 우선 사용하되 송신 측 출력만 확보한 항목은 표에 표시했습니다. 병렬 전송과 별도 다운로드 테스트의 반복 횟수는 결과에 구분했습니다.

## 4. 중계 서버 경유 경로와 외부 전송 성능

### 4.1 측정 구성

외부 노트북 또는 EC2를 송신 장비로 사용했습니다. 중계 서버를 통해 GPU에 SSH로 접속하고, `ssh -L`로 로컬 TCP 포트를 GPU의 iperf 포트에 연결했습니다.

### 4.2 중계 서버 경유 경로의 처리량과 지연

출발지를 노트북과 EC2로 바꿔 노트북 측 회선의 영향을 살펴봤습니다. 아래 네 경로는 모두 중계 서버를 경유했으며 iperf2로 측정했습니다. 처리량은 출발지에서 GPU로 전송한 결과이고, RTT는 왕복 측정값입니다.

| 출발지 → 목적지 | 평균 수신 처리량 | 평균 RTT |
|---|---:|---:|
| 노트북 → GPU1 | 66.63Mbps | 19.302ms |
| 노트북 → GPU2 | 67.03Mbps | 22.429ms |
| EC2 → GPU1 | 63.73Mbps | 8.649ms |
| EC2 → GPU2 | 69.60Mbps | 12.565ms |

노트북에서 두 GPU로 동시에 전송했을 때는 GPU1이 평균 40.77Mbps, GPU2가 34.03Mbps였습니다. 합계 약 74.80Mbps는 공통 경로의 자원 경쟁을 시사합니다.

노트북과 GPU2 사이의 RTT 테스트에는 타임아웃 경고가 1건 기록됐습니다.

### 4.3 아웃바운드 전송

교내 GPU에서 중계 서버를 거치지 않고 EC2로 보낸 iperf3 수신 처리량은 6회 평균 **94.02Mbps**였습니다.

EC2 로그의 출발 주소는 두 GPU가 공유하는 공인 IP이며, 회차별 송신 서버 식별 정보는 없습니다.

### 4.4 병목 검토

GPU1은 100Mbps 링크가 확인됐습니다. GPU2는 NIC가 1Gbps이지만, 출발지를 노트북에서 EC2로 바꿔도 중계 서버 경유 처리량이 크게 개선되지 않았습니다. 두 GPU의 동시 전송 결과와 함께 보면 중계 서버와 GPU 측 상위 연결 등 공통 경로의 제한을 검토할 필요가 있습니다.

병목 위치를 확인하려면 공유기 업링크, 중계 서버 회선과 속도 제한 정책을 점검해야 합니다.

## 5. NetBird 오버레이 연결과 성능 검증

### 5.1 NAT 특성과 UDP 통신 가능 여부

직접 연결을 시도하기 전에 두 GPU에서 `tailscale netcheck`를 실행했습니다.

| 결과 | 관측 내용 |
|---|---|
| `UDP: true` | 테스트한 외부 STUN 서버와 UDP 통신 성공 |
| `MappingVariesByDestIP: false` | 검사한 목적지 IP 사이에서 NAT 매핑 변화가 관측되지 않음 |

GPU1의 `turnutils_natdiscovery` 결과는 Endpoint-Independent Mapping과 Address-and-Port-Dependent Filtering으로, 전통적인 분류의 **Port Restricted Cone NAT에 해당하는 동작**이었습니다. 필터링 판정은 응답 출발 IP 또는 포트를 바꿨을 때의 타임아웃을 근거로 합니다.

### 5.2 NetBird 구성과 SSH 접속 검증

노트북과 GPU2에 NetBird 클라이언트를 설치하고 EC2의 NetBird 서버에 등록했습니다. Management 서비스는 장비 인증, 오버레이 IP와 접근 정책을 관리합니다. 클라이언트는 STUN으로 외부 주소와 포트를 확인하고 Signal 서비스를 통해 연결 후보를 교환합니다.

P2P가 성립하면 작업 데이터는 중계 서버를 거치지 않고 양쪽 클라이언트 사이의 WireGuard 암호화 터널로 전달됩니다. 중앙 서버는 장비와 정책을 계속 관리하며, 직접 연결이 어려울 때는 Relay 서버가 암호화된 데이터를 전달합니다.

설치 스크립트와 확인된 노트북 클라이언트 버전은 0.79.0입니다.

![중계 서버 경유 경로와 NetBird P2P 경로의 데이터 흐름](중계서버_NetBird_비교.png)

| 검증 항목 | 결과 |
|---|---|
| 노트북과 GPU2의 오버레이 IP | `100.84.*.62` / `100.84.*.130` |
| 장비 간 연결 상태 | `Connected`, `Connection type: P2P` |
| 관리 서버 연결 | 정상 |
| GPU2 오버레이 IP를 통한 SSH 로그인 | 성공 |

### 5.3 RTT와 TCP 처리량

| 접속 경로 | 응답 수 | 평균 RTT | 최대 RTT |
|---|---:|---:|---:|
| 중계 서버 경유 SSH 포워딩 | 90개 | 22.429ms | 657.904ms |
| NetBird P2P | 90개 | 9.064ms | 19.967ms |

처리량은 업로드와 다운로드를 나눠 측정하고, 단일 연결의 제약인지 확인하기 위해 4개 병렬 연결도 테스트했습니다. 업로드는 노트북 → GPU2, 다운로드는 GPU2 → 노트북입니다.

| 테스트 | 처리량 | 측정 위치 |
|---|---:|---|
| 업로드, TCP 연결 1개 | 3회 평균 34.20Mbps | 노트북 송신 측 |
| 업로드, TCP 연결 4개 병렬 | 1회 합계 26.9Mbps | 노트북 송신 측 |
| 다운로드, TCP 연결 1개 | 1회 9.23Mbps | 노트북 수신 측 |
| 다운로드, 패킷 캡처를 동반한 별도 테스트 | 1회 7.41Mbps | 노트북 수신 측 |

평균 RTT는 중계 서버 경유 경로보다 짧았지만, 연속 전송에서는 수신 중단과 낮은 처리량이 나타났습니다. 병렬 연결 테스트에서도 개선은 관측되지 않았습니다. RTT와 업로드 테스트 전후에는 P2P 상태를 확인했습니다.

### 5.4 UDP 처리량과 패킷 손실

TCP 전송 중단의 원인을 살펴보기 위해 UDP 부하 테스트을 추가했습니다. WireGuard는 TCP를 포함한 IP 패킷을 UDP로 운반하므로, 테스트 트래픽 자체의 TCP 재전송과 송신량 조절 없이 수신 상태를 확인하려는 목적입니다.

GPU2의 오버레이 TCP 상태에 표시된 `pmtu:1280`을 고려해 데이터그램은 1,200바이트로 설정했습니다. 부하를 낮춰 전송 중단의 재발 여부를 확인했습니다.

| 방향과 테스트 조건 | 수신 처리량 | 손실률 |
|---|---:|---:|
| 업로드, 초기 테스트 | 89.6Mbps | 14.59% |
| 업로드, 송신 부하 `-b 50M` | 52.5Mbps | 0.035% |
| 다운로드, 초기 테스트 | 37.6Mbps | 61.36% |
| 다운로드, 송신 부하 `-b 20M` | 9.27Mbps | 52.13% |

iperf2의 `50M`은 약 52.43Mbps, `20M`은 약 20.97Mbps입니다. 업로드는 부하를 낮추자 손실이 줄었지만, 다운로드는 `20M`에서도 합계 14초간 수신이 중단됐습니다. 정상 구간의 약 21Mbps에 비해 전체 처리량이 크게 낮아졌습니다.

손실률은 수신 패킷 번호로 집계한 값입니다. 일부 UDP 테스트의 연결 모드는 미기록 상태입니다.

### 5.5 TCP 상태와 패킷 캡처 분석

`ss`와 양쪽 장비의 패킷 캡처로 전송 중단 시 TCP 동작을 확인했습니다.

| 확인 자료 | 관측 내용 | 해석 |
|---|---|---|
| GPU2의 TCP 상태 | `cwnd:1`, 재전송 타임아웃 1.752초, 누적 재전송 1,790회 | 혼잡 윈도 축소와 재전송 대기 발생 |
| 양쪽 TCP 캡처 | 같은 데이터가 반복 재전송된 뒤 약 3.633초 만에 수신 | 전달 누락과 TCP 복구 동작 확인 |
| ACK와 중복 데이터 | 한쪽의 ACK가 상대 캡처에서 확인되지 않은 뒤 중복 데이터 수신 | ACK 전달 문제 가능성 |

TCP 재전송과 혼잡 윈도 축소가 처리량 저하에 관여했습니다. 패킷 누락 위치를 확인하려면 외부 UDP와 양쪽 TCP의 완전한 캡처가 필요합니다.

## 6. 운영 방향

### 6.1 외부 접속 방식

**초기 서비스는 상시 중계 방식을 제안합니다.** 현재 중계 서버 경유 경로에서 확보한 처리량과 NetBird 연속 전송의 긴 수신 중단을 고려한 판단입니다. 별도의 오버레이 클라이언트 없이 SSH와 SFTP를 사용할 수 있다는 점도 운영상의 이점입니다.

NetBird는 P2P 연결과 SSH 접속이 가능하고 RTT도 짧았지만, 전송 안정성을 개선해야 합니다. 상시 중계 방식은 대역폭 공유, 중앙 서버 장애와 트래픽 비용을 고려해야 합니다.

운영용 EC2 중계 서버는 GPU가 먼저 연결하는 `ssh -R` 방식으로 구성할 수 있습니다. 이번 측정 경로와 다른 구성이므로 실제 사용 성능은 별도 검증이 필요합니다.

### 6.2 NAS 연결 방향

NAS는 GPU 노드에서 교내망으로 직접 마운트해 저장소 트래픽을 외부 중계 경로와 분리하는 구성을 우선 검토합니다. 실제 마운트 가능 여부와 성능은 장비 도입 후 확인해야 합니다.
