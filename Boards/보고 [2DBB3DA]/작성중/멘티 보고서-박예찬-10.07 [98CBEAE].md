## 관찰 내용

- 김상현 멘토의 교내망 조사 보고서를 읽었다. 학교 방화벽은 밖에서 안으로 들어오는 접속을 막기 때문에, 외부에서 GPU 서버에 바로 접속할 수 없다는 문제가 있었다. 
- 이 문제를 풀기 위해 두 가지 방법(중계 서버 방식, NetBird 방식)의 속도를 직접 측정해서 비교했다. NetBird는 응답은 빨랐지만 큰 파일을 보낼 때 자주 끊겨서, 처음에는 더 안정적인 중계 서버 방식을 쓰자고 제안했다. 
- TF장님이 외부 사용자가 처음 접속하는 서버(진입점)는 AWS에 두고, 학교에는 GPU 서버와 NAS만 두기로 결정했다. 
- 10/6부터 김유리, 김상현 멘토가 제2연구실의 새 장비(A6000 GPU 서버, NAS)로 실험을 시작했다. 다른 연구실 장비라서, 프로그램을 설치할 때 바꾼 내용을 기록해 두고 끝나면 되돌리기로 정하는 과정을 보았다. 
- 개발팀이 GitHub에서 코드를 함께 관리하는 규칙(작업별로 브랜치를 따로 만들고, 검토를 거쳐 합치는 방식)을 읽었다.

## 이해 내용

- 이 프로젝트는 연구실마다 따로 가진 GPU를 여러 학생과 연구자가 나눠 쓸 수 있게 하는 플랫폼을 만드는 것이다. 
- 사용자는 크기를 골라 자기만의 작업 공간(인스턴스)을 받는다. 이 작업 공간은 Docker 컨테이너로 만들어서 사용자끼리 파일과 프로그램이 섞이지 않는다. 
- Docker와 HAMi는 역할이 다르다. Docker는 사용자마다 파일, 실행 중인 프로그램, 네트워크를 분리하고, HAMi는 Docker가 하지 못하는 GPU 메모리(VRAM) 제한을 맡는다. 그래서 둘을 함께 써야 한다.
- GPU 메모리(VRAM)는 Docker로 나눌 수 없어서 HAMi라는 프로그램을 쓴다. HAMi는 사용자마다 VRAM 한도를 정해 주고, 한도를 넘으면 그 사용자의 프로그램만 멈춘다. 그래서 한 카드를 여러 명이 안전하게 같이 쓸 수 있다. 
- 사용자 파일은 NAS(여러 서버가 같이 쓰는 저장 장치)에 보관해서, 작업 공간을 껐다 켜도 파일이 남는다. 
- MVP의 목표는 서버 한 대에서 "작업 공간 만들기 → 접속하기 → 한도 안에서 학습하기 → 끄고 반납하기"가 끝까지 되는 것이다. 지금 개발팀의 작업은 이 흐름을 가능하게 하기 위한 준비 단계다.
- 진입점을 AWS에 두는 이유는 학교 방화벽 밖에 있어서 외부 사용자가 접속할 수 있기 때문이다. 학교 안의 GPU 서버가 AWS 쪽으로 먼저 연결을 열어 두고, 사용자는 AWS를 거쳐 GPU 서버에 들어간다.

## 질문 사항

- NetBird는 왜 업로드보다 다운로드할 때 데이터가 더 많이 손실되는가? 
- 지금은 TF장님 자택 서버를 중계 서버로 쓰고 있는데, AWS로 옮기면 속도가 더 좋아지는가? 
- 여러 서버를 함께 쓰게 되면, 사용자를 어느 서버에 배정할지는 어떻게 정하는가?
- 학생 여러 명이 동시에 작업 공간을 켜고 끄면 NAS에서 홈 폴더를 한꺼번에 주고받게 되는데, 이때 NAS 속도가 느려지는 않는가?
