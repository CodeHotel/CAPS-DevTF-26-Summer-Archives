## 요약
이번 조사는 외부 사용자가 교내 GPU 서버에 접속하고, 작업 데이터를 NAS에 저장할 수 있는 네트워크 구성을 확인하기 위해 진행했습니다.
GPU 서버에서 EC2로 SSH 역방향 터널을 연결한 결과, EC2와 GPU 사이의 평균 RTT는 약 4ms였으며 GPU에서 EC2로의 수신 처리량은 약 93Mbps였습니다. 기존 중계 서버를 거치는 경로보다 평균 지연이 짧고 처리량도 높아, MVP의 사용자 접속 방식으로 제안합니다. NetBird는 직접 연결에 성공했지만, 이번 테스트 환경에서는 다운로드 중 수신 중단과 높은 손실률이 발생했습니다.
두 GPU를 동시에 사용해도 외부 전송 합계는 약 91~93Mbps로 유지됐습니다. 따라서 GPU 서버를 추가하더라도 현재 공유 경로의 전송 용량이 함께 늘어나지는 않을 것으로 판단됩니다. 대용량 다운로드 중에는 평균 RTT가 약 12ms에서 184ms로 증가했으므로, 파일 전송 속도를 제한해 SSH 응답성을 유지할 필요가 있습니다. 실제 SFTP 속도 제한 테스트에서는 SSH 명령 300회와 신규 로그인 48회가 모두 완료됐습니다.
NAS는 GPU 서버에서 SMB로 직접 연결하는 구성을 제안합니다. 세 GPU 서버에서 NAS의 TCP 445 포트 접근을 확인했고, GPU1에서는 SMB 인증과 마운트까지 확인했습니다. 쓰기 권한 문제로 파일 저장과 성능 검증은 완료하지 못했으므로, 사용할 NAS의 권한을 확보한 뒤 확인해야 합니다.
MVP에서는 HTTPS로 작업 생성과 종료 요청을 전달하고, SSH 역방향 터널로 사용자 접속을 제공하며, 학습 데이터는 GPU와 NAS 사이에서 직접 읽도록 구성합니다. 남은 핵심 작업은 이 세 경로를 실제 컨테이너에 연결하고, 사용자별 접근 제한과 파일 보존을 검증하는 것입니다.
